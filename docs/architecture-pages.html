System overview

The form owns the config; the agent advises and proposes

The Java backend sends the JSX once and rebuilds the config on every event. The frontend forwards what it received. The agent never writes the config: every change takes the same path as the user’s own input.

Principles

The config is the source of truth

Form state is not kept in the agent’s memory: it is rebuilt from the incoming config every turn, so it never needs syncing or summarizing.

The core knows no domain

A loan, a barbershop booking, a calendar: everything domain-specific comes from outside (domain packs, managers’ documents, skills). The core changes only with the component library.

Small context

The model sees a collapsed outline, the open section and the changes: about 1K tokens instead of about 16K for the loan form’s raw config. The rest is available through tools.

Append-only history

The system prompt is frozen per thread and updates arrive in new messages. This keeps prompt caching working and keeps models that bind reasoning to the prefix happy.

One turn

From a user message to an answer or a card

Every message brings a fresh config. The graph diffs it against the previous snapshot, compacts the history if needed, and calls the model and its tools. When the model proposes field values, the graph stops at an interrupt until the user answers.

What the model sees

A collapsed outline, the open section and the changes

Structure and order come from the JSX, deterministically; labels, flags and values come from the config. No model is involved in building the context.

Flags are inherited

A field inside a hidden or disabled container is hidden or disabled too. Progress counts only fields that can be filled.

Dependencies by observation

The config never says what a field depends on. The agent records what changed after a single-field edit and shows it as a “usually appears when…” hint.

Business documents

Managers upload documents; each form sees its scope

Documents go into a namespace (the form id by default). Scopes say which namespaces a form sees: its own and, for example, the bank’s shared documents. Then two layers: compilation into the domain pack, and a researcher for rare questions.

Why not a deep agent for everything

A form chat is many short turns. The deep-agent harness would add its overhead to each of them. Only document work is delegated, and everything the researcher reads stays in its own context.

Checked in live runs

  • “Omar does not work on Mondays”: only in the documents, not in the form
  • “Late-payment penalties?”: an honest “the documents do not say”
  • Recompiling during a conversation does not break the thread

User documents

A scan is read separately and never enters the history

The user attaches a letter, a business card or a scan. A separate vision call gets the document and the form’s field catalog and returns only the values found. The main conversation sees values, not the image.

A live example

An employment letter: the agent first chose “employed” to unlock the employer block, filled the tax id, position and start date, put the name back into the nominative case and warned about the “SAMPLE” watermark.

PII

Values of PII fields reach the model as <filled>. What the user types or attaches is seen by the model by design; strict regimes need tokenization before the model call.

Long conversations

Compact the dialogue, not the form

The form state is rebuilt from the config every turn, so it never needs summarizing. What grows is the per-turn context blocks (about 1K tokens each, stale immediately), tool results and the dialogue itself. That is what gets compacted.

GoalWhat the user is applying for at all

Decisions and preferencesAgreements (“fill the consents once the tab unlocks”)
Rejected or declinedSo rejected changes are not proposed again
Open questions / next stepWhere the conversation stopped

The “Invalid signature in thinking block” error

Claude Opus 5.5 binds reasoning blocks to the exact conversation prefix, including the system prompt. The prompt used to be rebuilt every turn and included rules from documents. When the documents were recompiled during a conversation, the prompt changed and the provider rejected every earlier block.

The fix

  • The system prompt is frozen per thread
  • Knowledge updates arrive as <updated_instructions> in a new message
  • If the provider still rejects old reasoning, one retry without it
  • Compaction removes reasoning from the kept turns

Checked

  • Recompiling documents during a live conversation: 0 errors
  • A 3,000-token threshold with 1 verbatim turn: the code word from the first message survived compaction and was entered once the tab unlocked

Configuration

Install or copy it, then configure

The formguide library does not depend on a transport or a UI. demo/ is an example integration: a mock form backend, a FastAPI app and a frontend. Every domain and every provider is set in the configuration, in code or YAML.

backend/
  formguide/                 the library
    guide.py                 FormGuide: register_form · run (AG-UI events) · compile_knowledge
    config.py                GuideConfig, load_config(yaml)
    models.py                models per role: agent · research · compile · extract
    skills.py                SKILL.md + LangChain tools, scoped to forms
    server.py                optional FastAPI router
    form/                    layout (ComponentMap) · overlay · diff · context rendering
    agent/                   graph · tools · prompt · memory (compaction)
    domain/                  Domain Pack: inline › provider › packs › dir › default (+ documents)
    knowledge/               storage · index (BM25 | VectorStore) · scopes · compile · researcher
    attachments/             user attachments and extraction
  demo/                      example: app.py · formguide.yaml · skills/ · domain_packs/ · mock_forms/

In code

from formguide import FormGuide, load_config
from formguide.server import create_router

guide = FormGuide(load_config("formguide.yaml"))
app.include_router(create_router(guide), prefix="/agent")   # or call guide.run(...) directly

Model requirements

  • agent and researcher: tool calling
  • compile and extract: structured output
  • extracting from scans: vision / PDF input

Checked

25 offline tests including real request payloads for ChatOpenAI, AzureChatOpenAI and ChatAnthropic. Live runs used Claude; OpenAI and Azure were not run live (no keys).
