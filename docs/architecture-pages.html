System overview

The form owns the config; the agent advises and proposes

The Java backend sends the JSX once and rebuilds the config on every event. The frontend forwards what it received. The agent never writes the config: every change takes the same path as the user’s own input.

Source: guide.py __init__.py architecture.md README.md specs/

Principles

The config is the source of truth

Form state is not kept in the agent’s memory: it is rebuilt from the incoming config every turn, so it never needs syncing or summarizing.

The core knows no domain

A loan, a barbershop booking, a calendar: everything domain-specific comes from outside (domain packs, managers’ documents, skills). The core changes only with the component library.

Small context

The model sees a collapsed outline, the open section and the changes: about 1K tokens instead of about 16K for the loan form’s raw config. The rest is available through tools.

Append-only history

The system prompt is frozen per thread and updates arrive in new messages. This keeps prompt caching working and keeps models that bind reasoning to the prefix happy.

Integrate

A standard AG-UI agent: CopilotKit and other clients connect as they are

One endpoint, POST /agent/run, takes an AG-UI RunAgentInput and streams AG-UI events validated against the official models. The form travels in state; cards are interrupts; frontend tools and prefill use the protocol’s own fields.

Source: agui.py server.py app.py prefill.py App.tsx api.ts spec.md

Five minutes to a running agent

pip install "formguide[all] @ git+https://github.com/denvasylenko/dushes.git#subdirectory=backend"
formguide init my-agent                        # formguide.yaml, a domain pack, a skill
formguide check --config my-agent/formguide.yaml   # loads it, calls no model
ANTHROPIC_API_KEY=... formguide serve --config my-agent/formguide.yaml --cors "*"

The only required setting is model:, e.g. "openai:gpt-5"; with no file at all, FORMGUIDE_MODEL does the same. Extras: anthropic, openai, server, research, sqlite; the core installs with LangGraph, LangChain core, Pydantic, PyYAML and pypdf only. In an existing service: app = create_app("formguide.yaml"), or create_router(guide) on your own FastAPI app.

CopilotKit

import { CopilotChat, CopilotKitProvider, HttpAgent, useAgent, useInterrupt } from "@copilotkit/react-core/v2"

const agents = { formguide: new HttpAgent({ url: "/agent/run" }) }   // no CopilotKit runtime server
<CopilotKitProvider agents__unsafe_dev_only={agents} agentId="formguide"><CopilotChat /></CopilotKitProvider>

agent.setState({ config, jsx_hash, form_id: "barber_booking" })         // before each run
useInterrupt({ render: ({ event, resolve }) => <Card value={JSON.parse(event.value)}
  onAnswer={(accepted, config) => resolve({ accepted, config })} /> })

The full example, with a frontend tool and prefill, is in examples/copilotkit. CopilotKit calls directly passed agents a development option; in production put a CopilotRuntime in front of the same HttpAgent, or use its selfManagedAgents. Nothing changes on the formguide side.

Any AG-UI client

import { HttpAgent } from "@ag-ui/client"

const agent = new HttpAgent({ url: "/agent/run", threadId })
agent.setState({ config, jsx_hash, form_id })
agent.addMessage({ id: crypto.randomUUID(), role: "user", content: "Where do I start?" })
await agent.runAgent({ tools: [getUserLocale] }, {
  onTextMessageContentEvent: ({ event }) => render(event.delta),
  onCustomEvent: ({ event }) => event.name === "on_interrupt" && showCard(JSON.parse(event.value)),
})

The demo frontend does exactly this: frontend/src/api.ts. To restore a chat after reopening, GET /agent/threads/{id}?format=agui returns the conversation as AG-UI messages for setMessages.

Prefill

Start from what your app already knows. Keys that are field names are validated directly; anything else (other keys, free text, attachments) goes through the extraction model. Values for locked or hidden steps are kept for later.

await agent.runAgent({ forwardedProps: { prefill: { data: { first_name: "Anna", gender: "Female" } } } })

# or on the server, without a chat
await guide.suggest_prefill(state, data=profile, text="moved to Lyon in 2021")
# -> {"values": [{"name": "gender", "value": {"id": "f", "name": "Female"}, "status": "now"}, ...], "errors": [...]}

Events

  • RUN_STARTED, then exactly one of RUN_FINISHED or RUN_ERROR
  • text, tool calls with results, CUSTOM: ui_directive, on_interrupt, agent_context, memory_compacted

Checked

  • CopilotKit 1.86: chat, card, frontend tool, prefill
  • @ag-ui/client 1.0.4: the demo frontend, restore after reload
  • every event validated against ag-ui-protocol in tests

One turn

From a user message to an answer or a card

Every message brings a fresh config. The graph diffs it against the previous snapshot, compacts the history if needed, and calls the model and its tools. When the model proposes field values, the graph stops at an interrupt until the user answers.

Source: graph.py tools.py prompts.py spec.md

syncDiffs the config against the snapshot, learns dependencies, builds the context, appends the messageSystem prompt frozen; knowledge updates arrive as <updated_instructions>
compactCompacts older turns into memory when the history is above the thresholdA failed compaction never blocks the turn
llmStreams the reply; withholds short internal notes before tool callsRetries once without reasoning blocks if the provider rejects them
toolsBuilt-in tools, skill tools and your own BaseTool; frontend tools the client declared end the runpropose_changes checks visibility, availability, read-only and options; client tools never shadow built-in ones
confirmInterrupt with the card; afterwards the form’s diff for the modelAn ignored card is closed on the next message
nudgeAsks the model to answer if it ended the turn silentlyAt most once per turn

What the model sees

A collapsed outline, the open section and the changes

Structure and order come from the JSX, deterministically; labels, flags and values come from the config. No model is involved in building the context.

Source: layout.py overlay.py render.py search.py spec.md

Flags are inherited

A field inside a hidden or disabled container is hidden or disabled too. Progress counts only fields that can be filled.

Dependencies by observation

The config never says what a field depends on. The agent records what changed after a single-field edit and shows it as a “usually appears when…” hint.

Business documents

Managers upload documents; each form sees its scope

Documents go into a namespace (the form id by default). Scopes say which namespaces a form sees: its own and, for example, the bank’s shared documents. Then two layers: compilation into the domain pack, and a researcher for rare questions.

Source: knowledge/ compile.py research.py packs.py kb/

Why not a deep agent for everything

A form chat is many short turns. The deep-agent harness would add its overhead to each of them. Only document work is delegated, and everything the researcher reads stays in its own context.

Checked in live runs

  • “Omar does not work on Mondays”: only in the documents, not in the form
  • “Late-payment penalties?”: an honest “the documents do not say”
  • Recompiling during a conversation does not break the thread

User documents

A scan is read separately and never enters the history

The user attaches a letter, a business card or a scan. A separate vision call gets the document and the form’s field catalog and returns only the values found. The main conversation sees values, not the image.

Source: extract.py prefill.py spec.md

A live example

An employment letter: the agent first chose “employed” to unlock the employer block, filled the tax id, position and start date, put the name back into the nominative case and warned about the “SAMPLE” watermark.

PII

Values of PII fields reach the model as <filled>. What the user types or attaches is seen by the model by design; strict regimes need tokenization before the model call.

Long conversations

Compact the dialogue, not the form

The form state is rebuilt from the config every turn, so it never needs summarizing. What grows is the per-turn context blocks (about 1K tokens each, stale immediately), tool results and the dialogue itself. That is what gets compacted.

Source: memory.py transcript.py spec.md spec.md

Two histories

The model’s history and the chat the user sees are stored apart. Compaction rewrites only the first, so a user who leaves and comes back sees the whole conversation, even after a server restart, and can still answer a pending card.

The “Invalid signature in thinking block” error

Claude Opus 5.5 binds reasoning blocks to the exact conversation prefix, including the system prompt. The prompt used to be rebuilt every turn and included rules from documents. When the documents were recompiled during a conversation, the prompt changed and the provider rejected every earlier block.

The fix

  • The system prompt is frozen per thread
  • Knowledge updates arrive as <updated_instructions> in a new message
  • If the provider still rejects old reasoning, one retry without it
  • Compaction removes reasoning from the kept turns

Checked

  • Recompiling documents during a live conversation: 0 errors
  • A 3,000-token threshold with 1 verbatim turn: the code word from the first message survived compaction and was entered once the tab unlocked

From a YAML file to a running guide

load_config("formguide.yaml") reads the file into a plain GuideConfig (you can still change it in Python); FormGuide(config) then builds one model per role and opens the stores. Paths in the file are relative to the file, ${VAR} is replaced from the environment, and "module:attr" strings are imported. formguide check --config … does all of this except calling a model. The full reference, key by key, is docs/configuration.md.

A complete YAML file

The shortest working file is one line. Everything below it is optional and shown with typical values; the demo’s file is backend/demo/formguide.yaml.

model: "anthropic:claude-opus-5-5"     # one model for every role, or per role:
models:
  agent:    {class: "langchain_openai:AzureChatOpenAI", azure_deployment: gpt-5,
             api_version: "2025-04-01-preview", azure_endpoint: "${AZURE_OPENAI_ENDPOINT}"}
  research: "openai:gpt-5-mini"
  extract:  {provider: anthropic, model: claude-opus-5-5, max_tokens: 8000}
components: {containers: {Tabs: tabs, Tab: tab, Accordion: accordion}, fields: {Input: text, Dropdown: select}}
domain_packs: {dir: domain_packs, provider: "my_app.packs:load_pack"}
knowledge:
  index: {factory: "my_app.vectors:make_store", filter: "my_app.vectors:ns_filter"}
  scopes: {loan_application: [loan_application, bank_common]}
skills: {dir: skills}
tools: ["my_app.tools:check_status"]
memory: {max_history_tokens: 60000, keep_turns: 4, model: "anthropic:claude-haiku-5-5"}
checkpointer: {sqlite: data/checkpoints.sqlite}   # model history
transcripts: {dir: data/transcripts}             # what the user saw
interrupt_mode: legacy                           # legacy | structured | both
